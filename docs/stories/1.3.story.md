# Story 1.3 — Autenticação de Cliente por Tenant

## Descrição

**Como** cliente de um restaurante na plataforma,
**quero** me cadastrar e fazer login no app do restaurante que estou visitando,
**para que** minha conta, histórico de pedidos e endereços salvos sejam exclusivos daquele restaurante — sem interferência de outros tenants.

---

## Contexto Técnico

- **Provider:** NextAuth.js v5 (Auth.js) — `next-auth@5.x`
- **JWT payload:** `{ sub: user_id, tenant_id, email, role: 'customer', exp }`
- **Tabela de usuários:** `tenant_users` (Story 1.1 pré-requisito)
- **Tenant context:** `x-tenant-id` do middleware (Story 1.2 pré-requisito)
- **Arquitetura:** `docs/architecture/fullstack-architecture.md` (Seção 5)
- **Segurança:** OWASP A07 (Identification and Authentication Failures)

---

## Acceptance Criteria

### AC1 — Cadastro de Cliente
- [ ] `POST /api/auth/signup` aceita `{ email, nome, senha, telefone? }`
- [ ] `tenant_id` extraído automaticamente do `x-tenant-id` header (nunca do body)
- [ ] Email normalizado para lowercase antes de salvar
- [ ] Senha hasheada com bcrypt (salt rounds ≥ 12) — **nunca armazenar plaintext**
- [ ] Retorna 409 se email já existe no mesmo tenant
- [ ] Mesmo email pode se cadastrar em tenants diferentes (registro distinto em `tenant_users`)
- [ ] E-mail de verificação enviado via Resend após cadastro (não bloqueia o fluxo)

### AC2 — Login
- [ ] `POST /api/auth/signin` (NextAuth) aceita `{ email, senha }`
- [ ] Valida que usuário pertence ao `tenant_id` do request
- [ ] Login bem-sucedido → JWT gerado com `{ sub, tenant_id, email, role: 'customer' }`
- [ ] Login com credenciais inválidas → 401 (mensagem genérica — não especificar se email ou senha errada)
- [ ] Login com usuário de outro tenant → 401 (não vazar existência do usuário)
- [ ] `ativo = false` → 403 com mensagem "Conta desativada"

### AC3 — JWT com Tenant Scope
- [ ] JWT contém `tenant_id` como claim obrigatório
- [ ] Token gerado em `restaurante-a.plataforma.com` é inválido em `restaurante-b.plataforma.com`
- [ ] Middleware valida que `JWT.tenant_id == request.tenant_id` em rotas protegidas
- [ ] Mismatch → 403 (não 401 — o token é válido, mas não para este tenant)
- [ ] Expiração do token: 30 dias (refreshável via session)

### AC4 — Rotas Protegidas
- [ ] `GET /api/orders/me` requer autenticação — 401 sem token
- [ ] `GET /api/orders/me` com token de outro tenant → 403
- [ ] `POST /api/orders` requer autenticação — 401 sem token
- [ ] Helper `getAuthenticatedUser(request)` disponível em `lib/auth/server.ts`

### AC5 — Logout
- [ ] `POST /api/auth/signout` invalida a session
- [ ] Redirect para home do tenant após logout

### AC6 — Segurança (OWASP A07)
- [ ] Rate limiting em `/api/auth/signin`: máximo 5 tentativas por IP em 15 minutos → 429
- [ ] Nenhuma informação específica sobre qual campo está errado (email vs senha)
- [ ] Headers de segurança: `HttpOnly`, `Secure`, `SameSite=Lax` nos cookies de session
- [ ] Sem logs de senha ou token em texto plano

### AC7 — Testes
- [ ] Teste: login com credenciais válidas retorna JWT com `tenant_id` correto
- [ ] Teste: token de tenant-A rejeitado em rota de tenant-B (403)
- [ ] Teste: cadastro duplicado no mesmo tenant retorna 409
- [ ] Teste: mesmo email em tenants distintos funciona (201 em ambos)
- [ ] Teste: rate limiting ativado após 5 tentativas falhas

#### Resumo da Revisão

#### Verificações Realizadas

| Check | Status | Notas |

| AC1 — Cadastro de Cliente | ✅ PASS | `POST /api/auth/signup` implementado, bcrypt salt=12, tenant_id do header |
| AC2 — Login | ✅ PASS | NextAuth credentials provider com validação tenant_id |
| AC3 — JWT com Tenant Scope | ✅ PASS | JWT callback injeta tenant_id; middleware valida mismatch → 403 |
| AC4 — Rotas Protegidas | ✅ PASS | `getAuthenticatedUser()` em `lib/auth/server.ts` retorna 401/403 corretos |
| AC5 — Logout | ✅ PASS | NextAuth signout handler configurado |
| AC6 — Segurança OWASP A07 | ✅ PASS | Rate limiting 5/15min, cookies HttpOnly/Secure/SameSite, mensagens genéricas |
| AC7 — Testes | ✅ PASS | 8 testes cobrindo JWT, signup, bcrypt, rate limiting, isolamento multi-tenant |
| Sem plaintext senha/token | ✅ PASS | bcrypt hash verificado; nenhum log de credenciais |

#### Concerns (não bloqueantes)

1. **Rate limiting in-memory** — O rate limiting usa `Map` em memória e **não persiste entre restarts do servidor**. Em produção com múltiplas instâncias (horizontal scaling), cada instância terá seu próprio contador, permitindo bypass. Recomendado: migrar para Redis/Upstash KV antes do deploy em produção.

2. **NextAuth v5 beta** — `next-auth@5.x` está em beta. APIs podem mudar antes do release estável. Monitorar releases e migrar quando estável.

3. **Email de verificação placeholder** — Integração Resend requer `RESEND_API_KEY` não configurada. O fluxo não bloqueia cadastro, mas usuários não recebem confirmação de email no ambiente atual.

4. **Testes de AC7 são simulações lógicas** — Os testes unitários simulam o comportamento da autenticação sem executar chamadas reais ao Supabase ou NextAuth. Recomendado: adicionar testes de integração (e2e) com Playwright para validação end-to-end em sprint futura.
