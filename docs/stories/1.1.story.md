# Story 1.1 — Infraestrutura Multi-Tenant e Banco de Dados

## Descrição

**Como** plataforma SaaS multi-tenant,
**quero** que o banco de dados isole completamente os dados de cada restaurante usando Row-Level Security,
**para que** nenhum tenant possa acessar — acidental ou intencionalmente — dados de outro tenant.

> Esta é a story mais crítica do projeto. Toda a segurança de dados da plataforma depende desta implementação.

---

## Contexto Técnico

- **Estratégia:** Row-Level Security (RLS) com `tenant_id UUID` em todas as tabelas multi-tenant
- **Função central:** `get_current_tenant_id()` via `current_setting('app.current_tenant_id', true)`
- **Schema completo:** `docs/architecture/database/schema.sql`
- **Migration plan:** `docs/architecture/database/migration-plan.md`
- **Arquitetura:** `docs/architecture/fullstack-architecture.md` (Seções 4 e 5)
- **Database:** Supabase (PostgreSQL 15+)

- [x] Função `get_current_tenant_id()` criada e funcional
- [x] Retorna `NULL` quando `app.current_tenant_id` não está definido (sem erro)
- [x] `SET LOCAL app.current_tenant_id = '<uuid>'` define o contexto corretamente
- [x] Função marcada como `SECURITY DEFINER` e `STABLE`

### AC3 — Tabelas Core
- [x] Tabela `tenants` criada com todos os campos do schema (slug, custom_domain, config JSONB, horarios JSONB, etc.)
- [x] Constraint `UNIQUE` em `tenants.slug` e `tenants.custom_domain`
- [x] Tabela `tenant_users` com constraint `UNIQUE(tenant_id, email)`
- [x] Tabelas `product_categories`, `products`, `orders`, `order_items`, `notifications` criadas
- [x] FK constraints com `ON DELETE` correto em todas as tabelas (ver schema.sql)
- [x] Campos monetários (`preco`, `subtotal`, `frete`, `total`) como `NUMERIC(10,2)` — **nunca FLOAT**

### AC4 — Triggers
- [x] Trigger `set_atualizado_em()` ativo em: `tenants`, `tenant_users`, `product_categories`, `products`, `orders`
- [x] Trigger `validate_order_total()` rejeita inserção de pedido com `total != subtotal + frete - desconto`
- [x] Trigger `record_order_status_transition()` registra timestamps automáticos de transição de status

### AC5 — Row-Level Security
- [x] RLS habilitado (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`) em: `tenant_users`, `product_categories`, `products`, `orders`, `order_items`, `notifications`
- [x] Tabela `tenants` **sem** RLS (resolvida via `service_role` no middleware)
- [x] Policies de isolamento criadas conforme `schema.sql` (seção RLS)

### AC6 — Índices
- [x] Índice `idx_tenants_slug` (unique) — resolução de subdomínio
- [x] Índice `idx_tenants_custom_domain` (unique, partial) — domínio customizado
- [x] Índice GIN `idx_products_search` para busca full-text em português (sem unaccent — MVP; habilitar via Dashboard > Extensions)
- [x] Demais índices do schema.sql criados

### AC7 — Teste de Isolamento ✅ BLOQUEANTE
- [x] Criar 2 tenants de teste via seed: `restaurante-a` e `restaurante-b`
- [x] Inserir 1 produto em cada tenant
- [x] Com `SET LOCAL app.current_tenant_id = '<uuid-restaurante-a>'`: `SELECT * FROM products` retorna **apenas** produtos do restaurante-a
- [x] Com `SET LOCAL app.current_tenant_id = '<uuid-restaurante-b>'`: `SELECT * FROM products` retorna **apenas** produtos do restaurante-b
- [x] Sem contexto definido: `SELECT * FROM products` retorna **zero registros** (não lança erro)
