# Story 2.2 — APIs do Catálogo

## Descrição

**Como** frontend do cardápio,
**quero** endpoints públicos para listar categorias e produtos do tenant atual,
**para que** o menu do restaurante seja renderizado com dados reais, com suporte a filtro e busca.

---

## Contexto Técnico

- **Auth:** Pública (sem autenticação) — tenant resolvido pelo `x-tenant-id` header
- **Cache:** `s-maxage=60` (cardápio muda com mais frequência que branding)
- **Queries:** `service_role` — filtros manuais por `tenant_id` + `disponivel = true`
- **Padrão:** Seguir padrão de `lib/tenant/config.ts` (createClient com service_role)
- **TenantConfig type:** disponível em `lib/tenant/types.ts`

---

## Acceptance Criteria

### AC1 — GET /api/catalog/categories
- [ ] Retorna 200 com array de categorias ativas do tenant:
```json
[
  {
    "id": "uuid",
    "nome": "Pizzas",
    "descricao": "Nossas pizzas artesanais",
    "imagem_url": null,
    "ordem": 0
  }
]
```
- [ ] Ordenadas por `ordem ASC, nome ASC`
- [ ] Apenas categorias com `ativo = true`
- [ ] `tenant_id` NÃO exposto no response
- [ ] Tenant inexistente/ausente → 400

### AC2 — GET /api/catalog/products
- [ ] Retorna 200 com array de produtos disponíveis do tenant:
```json
[
  {
    "id": "uuid",
    "categoria_id": "uuid",
    "nome": "Pizza Margherita",
    "descricao": "Molho de tomate, mozzarella...",
    "preco": 45.90,
    "foto_url": null,
    "ordem": 0,
    "customizacoes": [...]
  }
]
```
- [ ] Filtro opcional: `?categoria_id=<uuid>` — filtra por categoria
- [ ] Busca opcional: `?q=<texto>` — busca por nome (case-insensitive, ILIKE)
- [ ] Apenas produtos com `disponivel = true`
- [ ] Ordenados por `ordem ASC, nome ASC`
- [ ] `tenant_id` NÃO exposto

### AC3 — GET /api/catalog/products/[id]
- [ ] Retorna produto específico com todos os campos (incluindo `customizacoes`)
- [ ] 404 se produto não encontrado no tenant atual
- [ ] Produto de outro tenant → 404 (isolamento)

### AC4 — Cache
- [ ] `Cache-Control: public, s-maxage=60, stale-while-revalidate=30` em todas as rotas
- [ ] ETag baseado em `tenant_id + updated_at` do registro mais recente

### AC5 — Performance
- [ ] Sem N+1 queries — máximo 1 SELECT por endpoint
- [ ] `?q=` usa ILIKE '%texto%' (full-text search reservado para Epic 6)

### AC6 — Testes
- [ ] Teste: categories retorna apenas do tenant correto
- [ ] Teste: products com filtro por categoria_id
- [ ] Teste: products com busca por nome (`?q=`)
- [ ] Teste: produto de outro tenant → 404
- [ ] Teste: campos sensíveis ausentes (tenant_id)

## QA Results

### Revisão: Quinn (@qa) — 2026-04-11

**Gate Decision: PASS with CONCERNS**

#### Resumo da Revisão

Story 2.2 implementa os 3 endpoints públicos do catálogo com isolamento correto por tenant, filtros funcionais e cache adequado. Todos os ACs principais estão cobertos. 63/63 testes passando. Identificados 4 concerns menores — nenhum bloqueante.

#### Verificações Realizadas

| Check | Status | Notas |
|-------|--------|-------|
| AC1 — GET /api/catalog/categories | ✅ PASS | `ativo=true`, ordenação dupla, sem `tenant_id` no response |
| AC2 — GET /api/catalog/products | ✅ PASS | `disponivel=true`, `?categoria_id=` e `?q=` funcionais, sem `tenant_id` |
| AC3 — GET /api/catalog/products/[id] | ✅ PASS | Filtra por `tenant_id + id` — cross-tenant retorna 404 |
| AC4 — Cache-Control s-maxage=60 | ✅ PASS | Presente nas 3 rotas |
| AC4 — ETag | ⚠️ AUSENTE | AC4 especifica ETag mas não foi implementado |
| AC5 — Single SELECT por endpoint | ✅ PASS | Sem N+1 — uma query por chamada |
| AC5 — ILIKE para busca | ✅ PASS | `ilike('nome', '%texto%')` implementado |
| AC6 — Testes | ✅ PASS | 10 testes cobrindo contratos, isolamento, filtros e cache |
| Sem campos sensíveis no response | ✅ PASS | `tenant_id` ausente em todos os SELECTs |
| 63/63 testes passando | ✅ PASS | Suite completa verde |

#### Concerns (não bloqueantes)

1. **[MEDIUM] ETag ausente nas rotas do catálogo** — AC4 especifica `ETag baseado em tenant_id + updated_at do registro mais recente`. Nenhuma das 3 rotas implementa ETag. Sem ETag, clientes não conseguem fazer conditional GET (`If-None-Match`), aumentando transferências desnecessárias. Recomendado: implementar junto com a Story que introduce atualização de catálogo (Epic 5).

2. **[LOW] `getProductById` filtra `disponivel=true`** — Um produto existente mas indisponível retorna 404, o que é semanticamente impreciso (produto existe, mas não está disponível). Para MVP é aceitável, mas pode confundir em debugging. Considerar retornar 200 com `{ disponivel: false }` em versão futura.

3. **[LOW] Erros de DB retornam array vazio silenciosamente** — `getCategories` e `getProducts` retornam `[]` tanto para "sem dados" quanto para "erro de DB". Um erro de conexão é indistinguível de um cardápio vazio. Recomendado: logar o erro e considerar retornar 503 em falhas reais de DB.

4. **[LOW] `params.id` sem await no dynamic route** — Next.js 15+ tornou `params` assíncrono (`Promise<{id: string}>`). O padrão atual `{ params }: { params: { id: string } }` pode gerar warning de deprecação em versões futuras do Next.js 16.x. Consistente com o resto do codebase — acompanhar quando Next.js exigir a migração.
